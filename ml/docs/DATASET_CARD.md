# VIRGIL Advisor Training Dataset (v0.1)

Instruction-tuning corpus for fine-tuning a small LLM into the **VIRGIL Advisor**
— an endpoint-security agent helper that reasons about MITRE ATT&CK techniques,
detection logic, and host telemetry on behalf of the VIRGIL platform's
`python-worker` and `rust-worker` services.

This is the starter dataset (v0.1) built from deterministic, authoritative
sources. It is designed to be expanded with synthetic variants generated by a
strong teacher LLM (Claude, GPT) before final training.

## Methodology

Follows **CyberLLM-FINDS 2025** (arXiv 2601.06779): instruction-tuned domain
adaptation around MITRE ATT&CK using chain-of-thought (CoT) prompts and
structured (technique-anchored) ground truth, ready to be extended via synthetic
generation. The CyberLLM-FINDS authors targeted Gemma-2B; we target the 7B–14B
class (Qwen 2.5 7B, Llama 3.1 8B, Mistral 7B v0.3) for better context handling
and JSON-structured output reliability.

Three primary sources are blended:

| Source | What it gives us | Records |
|---|---|---|
| **MITRE ATT&CK STIX 2.1 enterprise bundle** | Taxonomy: techniques, tactics, groups, software, mitigations, **detection strategies (DETxxxx)** and **analytics (ANxxxx)** with concrete log-source references | 697 techniques (222 base + 475 sub), 7,480 procedure examples, 174 groups, 821 software entries |
| **SigmaHQ rules** | Real-world detection logic in YAML, with MITRE technique tags | 3,728 rules (87.4% MITRE-tagged), covering 396 distinct techniques |
| **SwiftOnSecurity sysmon-config** | Expert-authored Windows Sysmon rules with inline rationale (why this pattern is suspicious or benign) | 724 rule lines, 625 with explanatory comments |

Source repos are pinned in `raw/` and re-runnable from `scripts/`.

## Output: instruction examples (messages JSONL)

Format is OpenAI-compatible `messages` JSONL — drop-in for Axolotl, Unsloth,
TRL `SFTTrainer`, Together AI fine-tuning, and Fireworks fine-tuning.

```json
{
  "messages": [
    {"role": "system",    "content": "You are VIRGIL-Advisor..."},
    {"role": "user",      "content": "..."},
    {"role": "assistant", "content": "<reasoning>...</reasoning>\n<answer>{json}</answer>"}
  ],
  "meta": {"task": "event_to_technique", "source_ids": ["T1059.001", "..."], "split": "train"}
}
```

Every assistant turn uses **explicit `<reasoning>...</reasoning><answer>...</answer>`
tags**. The reasoning section is plain English CoT; the answer is structured JSON
that the VIRGIL worker can `json.loads` directly. This is the contract you'll
parse against in the worker.

## Task types

Seven task types, all generated deterministically from the three corpora above.
Task F (`event_to_technique`) is the production runtime task.

| Code | Task | What it teaches | Count (train/eval) |
|---|---|---|---|
| A | `technique_explanation` | Briefing on a technique with tactic phase, platforms, detection pointers | 628 / 69 |
| B | `procedure_to_technique` | TRAM-style: free-text observation → ATT&CK ID | 6,559 / 792 |
| C | `sigma_to_technique` | Given a Sigma rule YAML, identify the technique(s) it detects | 2,733 / 526 |
| D | `technique_to_detection` | "How do I detect technique X" → log sources + analytics | 628 / 69 |
| E | `sysmon_rationale` | Explain why a SwiftOnSecurity sysmon rule exists | 466 / 46 |
| **F** | **`event_to_technique`** | **Synthesized endpoint event → technique + confidence + recommended action** | **2,149 / 402** |
| G | `mitigation_recommend` | Technique → top MITRE mitigations | 526 / 60 |
| | **TOTAL** | | **13,689 / 1,964** |

### Split discipline

A held-out **10% of MITRE technique IDs** is reserved for evaluation. Every
example whose primary `technique_id` is in the eval set goes to `virgil_eval.jsonl`,
regardless of task. This means **no technique bleeds across train/eval** through
different task types — the model genuinely has to generalize. For records with
no associated technique (a small minority of Task E sysmon rules), a separate
deterministic hash-based 10% holdout is applied.

## Token statistics

| Split | Examples | Tokens | Avg | Max |
|---|---:|---:|---:|---:|
| Train | 13,689 | 5,836,133 | 426 | 1,148 |
| Eval | 1,964 | 853,553 | 434 | 1,088 |

Counts are estimated (3.8 chars/token, calibrated against cl100k_base). Replace
with `transformers.AutoTokenizer` on your exact base model before final training.

**Training-cost estimate:** 5.8M train tokens × 3 epochs = 17.5M tokens. At
~7,000 tok/s on a single A100 80GB QLoRA setup, that's ~42 minutes.

- Lambda A100 80GB @ $2.79/hr → **~$2** per full training run
- Lambda H100 SXM @ $3.99/hr (~1.6× faster) → **~$1.70** per run

You can afford to iterate a lot. Budget $50–$100 of credit for the whole project.

## Reproducing from scratch

```bash
# 1. Pull the three source corpora into raw/ (one-time, ~150MB total)
git clone --depth 1 https://github.com/mitre-attack/attack-stix-data.git raw/mitre-attack
git clone --depth 1 https://github.com/SigmaHQ/sigma.git                  raw/sigma
git clone --depth 1 https://github.com/SwiftOnSecurity/sysmon-config.git  raw/sysmon-config

# 2. Parse each source into clean intermediate JSONL
pip install pyyaml lxml
python3 scripts/parse_mitre.py
python3 scripts/parse_sigma.py
python3 scripts/parse_sysmon.py

# 3. Generate instruction examples
python3 scripts/build_instructions.py

# 4. Audit
python3 scripts/audit_dataset.py
```

Re-run any step independently when the upstream sources update — MITRE ATT&CK
publishes quarterly, SigmaHQ updates weekly.

## Expanding with a teacher LLM (recommended before final training)

The deterministic seed examples are **correct but template-flavored**. For
real-world robustness the model needs to see analyst language with the same
underlying ground truth. This is the "Synthetic data from a strong teacher"
pattern from the 2026 fine-tuning playbook.

```bash
# Preview prompts only — no API spend
python3 scripts/expand_synthetic.py --dry-run --seeds 10 --variants 3 \\
        --tasks event_to_technique,sigma_to_technique

# Live run (requires ANTHROPIC_API_KEY)
export ANTHROPIC_API_KEY=sk-...
python3 scripts/expand_synthetic.py \\
        --seeds 500 \\
        --variants 4 \\
        --tasks event_to_technique,procedure_to_technique,sigma_to_technique \\
        --model claude-haiku-4-5-20251001 \\
        --out instructions/virgil_train_synthetic.jsonl
```

Budget hint: ~$0.50–$2 per 1,000 variants on Haiku, ~$5–$15 on Sonnet. Target
3–5× expansion of Task B, C, F for the biggest training-time payoff (those are
the runtime-critical tasks).

After expansion, concatenate seed + synthetic for training:

```bash
cat instructions/virgil_train.jsonl instructions/virgil_train_synthetic.jsonl \\
    > instructions/virgil_train_full.jsonl
```

Keep `virgil_eval.jsonl` **un-augmented** — the eval set is your ground truth
for measuring improvements honestly.

## Fine-tuning quickstart (Axolotl on Lambda A100 80GB)

```yaml
# virgil-qwen7b.yml
base_model: Qwen/Qwen2.5-7B-Instruct
tokenizer_type: AutoTokenizer
is_qwen_derived_model: true

load_in_4bit: true
adapter: qlora
lora_r: 16
lora_alpha: 32
lora_dropout: 0.05
lora_target_linear: true

datasets:
  - path: instructions/virgil_train_full.jsonl
    type: chat_template
    chat_template: chatml
    field_messages: messages

sequence_len: 2048
sample_packing: true
pad_to_sequence_len: true

num_epochs: 3
micro_batch_size: 1
gradient_accumulation_steps: 8
learning_rate: 0.0002
lr_scheduler: cosine
optimizer: paged_adamw_32bit
warmup_steps: 50
bf16: true
gradient_checkpointing: true
flash_attention: true
logging_steps: 10

output_dir: ./virgil-qwen7b-lora
```

```bash
# On a Lambda 1× A100 80GB instance
accelerate launch -m axolotl.cli.train virgil-qwen7b.yml
```

For Llama 3.1 8B substitute `base_model: meta-llama/Llama-3.1-8B-Instruct` and
`chat_template: llama3`. Everything else stays the same.

## Evaluation harness (sketch — run after training)

The eval split is designed to be scored on three axes:

1. **Technique-ID exact match** — for tasks B, C, F, G: parse `<answer>`,
   compare `technique_id` (and `primary_technique`) to ground truth.
2. **Tactic recall** — for tasks A, B, F: did the model name the right tactic
   short_names?
3. **Structural validity** — does every assistant turn produce parseable
   `<reasoning>...</reasoning><answer>{valid_json}</answer>`?

If exact-match F1 on Task F (event_to_technique) lifts by ≥ 5 percentage points
over the stock base model, the fine-tune is doing real work. If not, the
dataset is the problem before the training recipe is.

## Known limitations and roadmap

**v0.1 limitations to fix in v0.2:**

- **Heavy Windows skew** (75% of Sigma rules, all of sysmon-config). Add Linux
  auditd rules (e.g. Wazuh's ruleset) and macOS endpoint security rules.
- **No malware-family corpus** — the model can't yet recognize concrete
  IOC-style signatures. Add MalwareBazaar / VirusShare summaries.
- **Procedure-to-technique examples cluster around well-documented techniques**
  (the procedure_examples in MITRE are skewed toward popular APT groups).
  Mitigate with synthetic expansion across rare techniques.
- **No false-positive examples** — the model only sees malicious patterns
  labeled positive. Use Sigma `falsepositives` field and SwiftOnSecurity
  `exclude` rules in a future task type "is this benign?".
- **No multi-step incident reasoning** — every example is single-event.
  Future task: kill-chain stitching across multiple correlated events.

**Source-update cadence:**

- MITRE ATT&CK: quarterly (October, January, April, July)
- SigmaHQ: weekly main-branch merges
- SwiftOnSecurity sysmon-config: ad hoc

Bump source repos and re-run the pipeline; nothing else changes.
